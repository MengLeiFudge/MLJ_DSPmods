# 万物分馏设计案

适用版本：
- FE 2.3
- 基线分支：master

本文是 FractionateEverything 的正式设计事实源，用于先定义模组最终形态，再与当前实现比对，最后进入 plan 阶段决定改哪里、怎么改、先后顺序和验证范围。

## 1. 设计方法

后续讨论和重构按“宏观到微观”推进：

1. 先确认模组外部承载面。
2. 再确认玩家阶段体验。
3. 再确认全局核心循环。
4. 再确认各承载面下的功能清单。
5. 再确认内部玩法系统、状态和接口。
6. 最后与当前实现逐项比对，形成差距表。

当前阶段只确认最终形态。实现顺序、迁移步骤、存档兼容、提交拆分和验证链属于后续 plan 阶段。

## 2. 一级承载面

模组从玩家接触面上分为三个部分：

1. 分馏塔。
2. 非分馏塔建筑，目前核心是物流交互站。
3. UI 面板。

这是外部承载面或功能入口划分，不是内部玩法系统划分。

内部玩法系统，例如抽取、路线、货币、建筑培养、市场补给、任务成就，可以通过这些承载面呈现或操作，但不应反过来打乱承载面边界。

另有一类必须单独拆分的底层系统：影响原版行为的系统。

拆分原因只有一个：
- 它们会改变或介入原版行为。

当前确认单独拆出的底层系统：
- 堆叠扩展系统。
- 原版配方强化系统。
- 数据中心，即物品存储系统。

不列入此类的例子：
- 黑雾战斗信息源系统。它只读取黑雾事实和状态，不直接改变原版行为，因此不按“影响原版行为的底层系统”处理。

## 3. 分馏塔

分馏塔负责自动化。

职责：
- 自动化生产、转化、复制、精馏和培养。
- 承接分馏配方运行。
- 处理流动输入、流动输出和产物输出。
- 提交真实运行事实，供路线成长、统计、任务等系统读取。

不负责：
- 抽取概率。
- UI 页面规划。
- 市场价格。
- 源点发放。
- 直接写入虚拟经验、成就点或货币变化。

设计原则：
- 前期需要手动的东西，后期应逐步被分馏塔或其他自动化建筑替代。
- 自动化产线不需要保底，因为产能会打破概率。
- 复杂度应主要存在于可自动化、可规划、可调参的内部链路。

最终分馏塔：
- 交互塔。
- 矿物复制塔。
- 转化塔。
- 精馏塔。

主线基线：
- 四种分馏塔对应四条主线基线。
- 每条基线都必须有足够内容和不同机制，不能只是同一种玩法换皮。

四条主线基线：
- BuildingTrain：围绕交互塔、原胚培养、建筑循环和分馏塔成长。
- MineralCopy：围绕矿物复制、资源扩展、黑雾材料读取和复制路线成长。
- Conversion：围绕物品转化、链条共享、单路锁定和转化路线成长。
- Rectification：把矩阵从原版科研资源加工为 FE 自己的矩阵精华，并围绕精华转化、精馏回流、成长催化和高密度票据形成实体产线。

已确认删除：
- 点数聚集塔。
- 点数聚集配方。
- PointAggregate 不作为最终路线家族、核心系统或长期兼容玩法保留。

### 3.1 分馏配方与塔处理语义

本节只定义最终形态下“有哪些配方”和“分馏塔如何处理这些配方”。配方获取、迁移步骤、提交拆分和验证链属于后续 plan 阶段。

当前四条主线的配方家族：

- BuildingTrain：原胚培养、返胚循环、定向原胚、数据中心消耗塔。
- MineralCopy：基础矿物复制、稀有矿物复制、流体资源复制、黑雾材料复制、兼容 MOD 资源复制、伴生副产物。
- Conversion：建筑升级链、物流/运输链、防御/弹药链、燃料链、消耗品链、黑雾材料链、兼容建筑/消耗品链。
- Rectification：矩阵萃取、精华压缩、精华回流、精华拆票、黑雾矩阵萃取、精华催化。

塔处理模型：

1. 通用三态模型。
   - 损毁。
   - 成功产出。
   - 直通输出。
   - 适合 MineralCopy，也适合部分 BuildingTrain 和 Conversion。
2. 目标锁定模型。
   - 在多输出链条中固定目标产物。
   - 保留损毁、成功、直通，但成功后的输出路径由塔设置决定。
   - 适合 Conversion。
3. 专用流转模型。
   - 输入、输出、回流、比例、阶段和损耗都由路线专用规则处理。
   - 不强求与普通配方完全同构。
   - 适合 Rectification。

BuildingTrain：

- 定义 FE 自己的塔生态。
- 让原胚、分馏塔、定向原胚和塔种强化形成循环。
- 后期允许通过链条达到无限分馏塔，这是成长目标，不是漏洞。
- 原胚培养和返胚循环是基础结构，不应拆成大量抽取项。
- 最终形态是自循环增殖出实体塔，实体塔送入数据中心后被消耗，并转成对应塔运行加成。
- 数据中心消耗塔不需要额外包装成“交互塔献祭配方”。分馏塔负责把塔增殖出来，数据中心负责消耗实体塔并承接加成。

MineralCopy：

- 输入是资源本身。
- 成功主输出应以同资源增殖为核心。
- 副产物可以体现矿物伴生关系，但不能喧宾夺主。
- 失败和直通可以沿用通用三态模型。
- 后期通过原料保留、产物翻倍、喷涂、塔成长、配方成长等条件达到净正收益。
- 基础矿物和常规流体应随阶段自然展开，不能全部依赖抽取。

Conversion：

- 输入是某条相关物品链上的物品。
- 成功输出可以是相邻层级、同层级或指定锁定目标。
- 单路锁定是核心机制之一，用于把随机转化链条变成可规划产线。
- 价值守恒可以作为前中期约束；后期允许在成长条件下净正收益。
- Conversion 不做万能等价交换。
- 严格禁止普通材料转化，避免破坏原版科技进程。

Rectification：

- 输入是矩阵或矩阵精华。
- 成功输出是实体矩阵精华、调相后的精华、回流精华或票据化资源。
- 精馏塔可以不完全沿用通用三态模型。
- 精馏应强调比例、方向、回流、损耗、阶段约束和自动化调参。
- 源点不进入精馏配方。
- 面板只展示、规划和确认，不直接把矩阵当 FE 成长货币扣掉。

### 3.3 配方成长入口

“奖池”不作为内部设计术语。后续讨论四条线时，不问“这个配方在哪个奖池抽”，而问“这个配方或抽取单位有哪些成长入口，各入口分别提升等级、回响、解锁、补差还是加速”。

统一模型：

- 配方运行经验：自动化产线主来源，负责配方等级。
- 抽取重复命中：手动或半手动补差来源，负责回响或定向加速。
- 阶段自然展开：随原版科技、矩阵阶段或塔种能力展开基础配方。
- 数据中心消耗：消耗实体塔、资源或精华，转成对应路线加成。
- 任务、成就和里程碑：一次性奖励或阶段性补差，不作为长期重复操作。

已确认原则：

- 配方升级的主来源统一为分馏塔产线运行事实，即“产线运行 = 累计经验”。
- 抽取和资源消费只能做方向、补差或加速，不应成为唯一升级来源。
- 配方升级不能要求玩家逐条点。
- 玩家可以设置升级偏好，例如优先线、优先家族、优先阶段。
- 后期必须能批量、自动、按策略消费资源。
- 自动化产线不需要保底；手动抽取必须有保底。

配方等级与回响：

- 配方等级建议统一为 Lv0-Lv5，代表产线熟练度。
- Lv3 是价值守恒或关键机制成型点。
- Lv4/Lv5 可以进入轻微净正收益，但需要玩家先投入矩阵、塔等级、配方成长和产线时间。
- 配方回响属于抽取单位，不一定属于单个底层配方，也不一定属于整个大主线。
- 回响建议为 0-3 档，负责重复抽取的附加能力。
- 没有回响也必须能完整自动化运行；回响不能提供核心产线门票。

术语：

- 底层配方：分馏塔真实运行的 RecipeKey。
- 配方家族：一类配方的进化路线与分类，例如矩阵萃取、精华压缩、精华回流、精华拆票。
- 抽取单位：玩家通过抽奖获得或重复命中的对象，可以是一条具体配方、一组同类配方、一个链条或一个家族能力。
- 配方回响：抽取单位重复命中后的 0-3 档附加能力。

### 3.4 四条线成长入口矩阵

本节记录暂定成长入口。具体体验等实现后再确认。

BuildingTrain：

- 基础展开：原胚培养和返胚是基础结构，随塔种阶段展开；塔种首次获得可以来自主抽取池或阶段奖励，但获取后应能进入自动化循环。
- 等级来源：交互塔实际运行培养/返胚配方，给对应塔种或对应配方家族累计经验；数据中心消耗实体塔可以给塔种加成经验，但不替代产线运行经验。
- 回响/抽取单位：塔种强化、定向原胚、数据中心消耗效率。
- 补差/加速：残片、定向原胚、多余实体塔、矩阵精华催化。
- 禁止事项：禁止让玩家逐个塔手动点献祭；禁止把塔成长变成纯 UI 扣资源；禁止高回响卡住基础塔循环。

MineralCopy：

- 基础展开：基础矿物和常规流体随阶段自然展开；稀有矿物、黑雾材料、兼容 MOD 资源可以作为抽取单位或路线节点。
- 等级来源：矿物复制塔运行对应资源复制配方，给该资源或资源组累计经验；同组资源可以共享部分经验。
- 回响/抽取单位：资源组、关键单资源、伴生条目。
- 补差/加速：残片补差资源组经验；矩阵精华按阶段催化对应资源组成长；黑雾战斗信息只作为事实来源，不承担消费和升级。
- 禁止事项：禁止玩家逐个矿物手动点升级；禁止基础资源复制全部依赖抽取；禁止用 MineralCopy 转化普通材料。

Conversion：

- 基础展开：与原版科技进程强绑定的基础链条，随原版阶段或相关物品可见性展开；特殊链条、高价值链条和提前建筑可以通过抽取单位解锁。
- 等级来源：转化塔运行对应链条配方，给该链条或抽取单位累计经验；单路锁定运行也应计入同一链条经验。
- 回响/抽取单位：链条条目、特殊跨层能力、单路锁定强化。
- 补差/加速：残片补差链条经验；矩阵精华按阶段催化对应链条成长；重复抽到已解锁链条时，优先补回响，满回响后转链条经验、残片或矩阵精华。
- 禁止事项：禁止普通材料转化；禁止用转化绕过原版科技主链；禁止把同一链条拆得过细，导致玩家必须抽大量方向配方。

Rectification：

- 基础展开：矩阵萃取随对应矩阵阶段自然展开；精华拆票随对应精华可见性展开；精华压缩、精华回流、黑雾矩阵萃取和精华催化可以作为抽取单位或路线节点。
- 等级来源：精馏塔运行对应精馏配方，给对应配方家族累计经验；矩阵萃取、压缩、回流分别成长，不混成一个大经验池；精华拆票不吃成长倍率，可以不设等级，或只作为自动化便利项。
- 回响/抽取单位：精华压缩、精华回流、黑雾矩阵萃取、精华催化。
- 补差/加速：消耗矩阵精华为同阶段或低阶段精馏家族加速；残片只做底层补差，不应替代精华链条；重复抽到精馏条目时，优先补回响，满回响后转矩阵精华或对应家族经验。
- 禁止事项：禁止源点进入精馏配方；禁止面板直接消耗矩阵作为 FE 成长货币；禁止让精华拆票成为精馏唯一价值；禁止把每个矩阵萃取都做成必须抽取的单项门票。

## 4. 非分馏塔建筑

非分馏塔建筑是 FE 中不承担分馏热路径、但仍承担实体建筑能力的部分。

当前核心：
- 行星内物流交互站。
- 星际物流交互站。

物流交互站职责：
- 物流交互。
- 数据中心连接。
- 上传下载。
- 槽位模式。
- 与物流系统相关的容量、堆叠、能耗和交互能力。

不负责：
- 分馏配方运行。
- 抽取结果。
- 路线成长公式。
- 市场价格。
- 源点产出。

设计原则：
- 物流交互站是建筑，不是 UI 页面，也不是路线系统。
- 它可以让玩家把物品和数据中心、物流网络连接起来，但不应承担分馏塔的自动化生产职责。
- 两个交互站是非分馏塔建筑承载面的当前全部内容；后续如果新增非分馏塔建筑，必须先说明它为什么不是分馏塔，也不是 UI 功能。

## 5. UI 面板

UI 面板负责查看、规划、手动确认和解释，不承担自动化生产。

职责：
- 主面板。
- 成长展示。
- 抽取偏好设置。
- 路线规划。
- 货币、精华和资源消费预览。
- 任务、成就、图鉴、统计和教程说明。

不负责：
- 自动化生产。
- 分馏热路径。
- 物流站运行。
- 直接修改其他系统内部状态。
- 直接消耗矩阵作为 FE 成长货币。

设计原则：
- UI 可以发起手动确认、消费请求或偏好设置。
- UI 不能成为生产机器。
- 手动重复操作必须有保底，不能让玩家无限重复无反馈。
- UI 外部入口应尽量简单，用简单外在内容承载更深内部策略。
- FE 已有精馏和自己的货币系统，因此面板不需要、也不应该直接消耗矩阵来升级。

## 6. 外部简单、内部复杂

简化不是削薄系统，而是简化不必要操作、入口和外部选择负担。

目标：
- 用非常简单的外在内容撑起更深的内部玩法。

例子：
- 抽取外部表现为一个主抽取池，而不是多个长期并列奖池。
- 玩家抽取前设置方向或偏好，而不是频繁切换奖池。
- 内部仍可通过偏好、阶段、权重、保底和资源投入形成策略。
- 精馏外部入口保持清晰，但内部通过矩阵精华、精华转化、回流、比例和调参形成深度。

## 7. 核心设计原则

已确认：

1. 分馏塔负责自动化。
2. UI 面板只做规划、消耗、查看和手动确认，不承担自动化生产。
3. 简化指简化外部入口、外部选择负担和重复操作，不等于削薄玩法系统。
4. 复杂度必须带来玩法收益，不能只是数值负担。
5. 前期手动、后期自动化替代，是模组意义的一部分。
6. 手动重复操作必须有保底。
7. 自动化产线不需要保底。
8. 虚拟数值不能直接作为分馏产物。
9. 源点是三层货币体系最高层，类比手游点券、钻石、付费石或充值货币，不能由产线产出。
10. 矩阵是原版科研资源和精馏输入，不是 FE 面板成长货币。
11. 主线不是顶层系统，而是多个系统共同呈现出来的玩家进度表达。

## 8. 矩阵、精华与面板消费边界

已确认：
- FE 面板不直接消耗矩阵作为成长货币。
- FE 已有精馏系统和自己的货币系统，不需要继续让面板吃矩阵。
- 矩阵的 FE 定位是精馏输入，而不是面板消费项。

设计理由：
- 如果面板可以直接消耗数据中心里的矩阵完成成长，那么矩阵精华就容易退化成“多绕一步的货币”。
- 精馏塔存在的意义，是把原版矩阵加工为 FE 内部可自动化流转、转化、回流和催化的实体资源。
- 成长应从“面板扣矩阵”转向“生产和规划矩阵精华链条”。

边界：
- 原版矩阵仍然保留原版科研意义。
- FE 可以读取矩阵阶段作为进度、解锁或约束条件。
- FE 的成长消费应使用 FE 自己的资源，例如残片、矩阵精华、源点或其他 FE 内部资源。
- 面板可以展示矩阵、矩阵精华和消费预览，但不直接把矩阵当作 FE 成长货币扣除。

## 9. 影响原版行为的底层系统

这类系统单独拆出来看。

拆分原则：
- 只因为它们影响原版行为。
- 不是因为它们一定是主线。
- 不是因为它们一定有独立玩法入口。
- 不是因为它们比其他系统更重要。

拆分收益：
- 后续设计可以先把“模组自己的玩法”与“对原版行为的影响”解耦。
- 修改这类系统时，必须额外关注原版兼容、热路径、全局副作用和存档影响。
- 不影响原版行为的系统，不应被混入这个底层分类。

### 9.1 堆叠扩展系统

归类原因：
- 它会改变或扩展原版相关的堆叠行为。

职责：
- 定义 FE 允许的堆叠上限。
- 为分馏塔、物流交互站、研究站、分拣器或其他相关原版行为提供堆叠边界。

不负责：
- 分馏配方内容。
- 抽取结果。
- 路线成长语义。

当前 2.3 代码证据：
- `FractionateEverything/src/Logic/Progression/StackingManager.cs`。
- `FractionateEverything/src/Logic/Progression/InserterStackPatch.cs`。
- `FractionateEverything/src/Logic/Manager/LabManager.cs`。

### 9.2 原版配方强化系统

归类原因：
- 它会读取并调整原版配方执行行为。

职责：
- 管理原版配方强化状态。
- 控制原版配方时间、上限或强化等级。
- 与矩阵阶段、堆叠扩展或全局成长形成约束关系。

不负责：
- 定义 FE 分馏配方。
- 替代路线成长系统。
- 直接承担抽取或市场补给。

当前 2.3 代码证据：
- `FractionateEverything/src/Logic/VanillaRecipes/VanillaRecipeManager.cs`。
- `FractionateEverything/src/UI/MainPanel/Operate/VanillaRecipeOperate.cs`。

### 9.3 数据中心 / 物品存储系统

归类原因：
- 它改变玩家背包、模组库存、建筑交互和资源读写路径。
- 它让 FE 资源可以脱离单个建筑或单次 UI 操作，在全局存储中被读取和消费。

职责：
- 全局物品存储。
- 上传下载。
- 玩家背包访问重定向。
- 奖励入库。
- 为分馏塔、物流交互站、抽取、市场、任务等系统提供统一库存边界。

不负责：
- 决定物品价值。
- 决定路线成长公式。
- 决定抽取概率。
- 生产资源。

当前 2.3 代码证据：
- `FractionateEverything/src/Logic/DataCenter/DataCenterInventory.cs`。
- `FractionateEverything/src/Logic/DataCenter/PlayerInventoryAccess.cs`。
- `FractionateEverything/src/Logic/Station/Runtime.cs`。

### 9.4 不属于本类的只读信息源

只读信息源不因为“被其他系统使用”就列入原版影响底层系统。

黑雾战斗信息源：
- 只读取黑雾阶段、击杀、掉落、威胁、材料可见性等事实。
- 不直接改变原版行为。
- 不直接写路线成长。
- 不直接发市场补给。
- 不直接决定经济价格。

因此，黑雾战斗信息源应作为信息源系统处理，不放进“影响原版行为的底层系统”。

## 10. 与内部系统的关系

一级承载面：
- 分馏塔。
- 非分馏塔建筑。
- UI 面板。

影响原版行为的底层系统：
- 堆叠扩展系统。
- 原版配方强化系统。
- 数据中心 / 物品存储系统。

内部玩法系统：
- 分馏产线系统。
- 精馏与矩阵精华系统。
- 抽取成长系统。
- 配方路线系统。
- 建筑培养系统。
- 三层货币系统。
- 市场补给系统。
- 任务成就与全局成长系统。
- 黑雾战斗信息源系统。
- 图鉴统计教程系统。

关系：
- 内部系统定义规则、状态、资源和成长。
- 一级承载面定义玩家从哪里看到它们、操作它们、自动化它们。
- 影响原版行为的底层系统定义 FE 与原版之间的边界和副作用。
- 一个内部系统可以通过多个承载面呈现。
- 一个承载面也可以承载多个内部系统。

红线：
- 不要把内部玩法系统误当外部承载面。
- 不要让 UI 承担自动化生产。
- 不要让黑雾、市场、路线、货币等内部系统越权拥有其他系统职责。
- 不要把只读信息源误归类为原版影响底层系统。
- 后续讨论模组自有玩法时，先把原版影响底层系统剥离出来，避免把原版副作用混进主线设计。

## 11. 当前 FE 2.3 实现差距表

- 迁移：当前有类似状态或逻辑，但主键、归属或边界不对。
- 改名/重归属：当前行为保留，但系统归属或命名错误。
