# 分馏塔

本文只描述万物分馏的目标最终设计，不描述完成度、实现差距、提交历史、构建结果或发布状态。

顶层按玩家接触到的承载面拆成三块：

1. 分馏塔。
2. 非分馏塔建筑。
3. UI 面板。

路线、成长、货币、市场、数据中心、黑雾信息源等不是新的顶层承载面，而是跨承载面的内部玩法系统。它们会放在最相关的承载面下说明其设计思路和边界。

整体目标是把“分馏”扩展成长期成长型自动化玩法：前期通过少量手动选择建立方向，中期把重复操作交给分馏塔、物流交互站和数据中心，后期通过路线成长、矩阵精华、建筑培养、任务目标和全局成长形成可规划的自动化链条。

## 分馏塔的总职责

分馏塔负责自动化。

它负责：

- 自动化生产、复制、转化、精馏和培养。
- 承接真实分馏配方运行。
- 处理输入、输出、回流、损耗、副产物和产物登记。
- 提交产线运行事实，供配方成长、路线成长、任务、统计和建筑培养读取。

它不负责：

- 抽取概率。
- UI 页面规划。
- 市场价格。
- 源点发放。
- 直接写入虚拟经验、成就点或货币变化。

设计原则：

- 前期需要手动的东西，后期应逐步被分馏塔或其他自动化建筑替代。
- 自动化产线不需要保底，因为产能和规模会自然打破概率波动。
- 虚拟数值不能直接作为分馏产物；产线应产出实体物品、运行事实或可被其他系统消费的明确资源。
- 后期允许在足够材料、时间、塔等级、配方成长和配套系统投入之后形成净正收益链；这是长期成长目标，不是漏洞。

净正收益口径：

- 净正收益只允许出现在明确输入、明确阶段门槛和明确成长投入之后。
- Lv3 通常是守恒或核心机制成型点；Lv4/Lv5 可以进入轻微净正收益。
- 净正收益不能来自无输入永动、UI 直接发放、市场套利或绕过原版科技阶段。
- 一条链允许净正收益，不等于所有中间环节都必须净正收益；早期环节可以有损，后期通过塔等级、配方成长、路线效果、矩阵精华或建筑投入补回。

## 四种分馏塔

最终分馏塔分为四种：

- 交互塔。
- 矿物复制塔。
- 转化塔。
- 精馏塔。

四种塔对应四条主要自动化基线：

- BuildingTrain：交互塔、原胚培养、塔生态、建筑循环和分馏塔成长。
- MineralCopy：矿物复制、资源扩展、黑雾材料读取和复制路线成长。
- Conversion：相关物品链转化、单路锁定、链条共享和转化路线成长。
- Rectification：矩阵萃取、矩阵精华、精华压缩、精华回流、精华拆票和成长催化。

四条线必须有不同机制，不能只是同一种玩法换皮。

最终不保留的方向：

- 点数聚集塔。
- 点数聚集配方。
- PointAggregate 路线家族。

物流交互站的增产点数池是物流交互站支撑能力，不是点数聚集塔的替代路线，也不是第五条分馏主线。

## 分馏塔处理模型

分馏塔的配方处理分三类。

### 通用三态模型

用于最接近普通分馏的配方。

三种结果：

- 损毁：输入被消耗，没有有效产出。
- 成功产出：输入按配方规则产出目标物或副产物。
- 直通输出：输入未发生有效转化，按原样或按配方指定形式输出。

适合：

- MineralCopy。
- 部分 BuildingTrain。
- 部分 Conversion。

### 目标锁定模型

用于一条链里存在多个可能输出，而玩家需要把随机链条变成可规划产线的场景。

设计思路：

- 保留损毁、成功、直通这些基础语义。
- 成功后的输出目标由塔设置或路线设置决定。
- 目标锁定可以付出损耗、效率或成长门槛，换取稳定方向。
- 锁定不是万能选择器，只能在已定义的相关链条内工作。

适合：

- Conversion。

### 专用流转模型

用于输入、输出、回流、比例、阶段和损耗都必须由专用规则控制的配方。

设计思路：

- 不强求和普通三态配方完全同构。
- 可以使用比例、方向、阶段、回流、压缩、损耗、调相等专用规则。
- 目标是形成可调参、可规划、可自动化的深层链条。

适合：

- Rectification。
- BuildingTrain 中涉及塔生态和献祭承接的部分规则。

## BuildingTrain：交互塔与分馏塔生态

BuildingTrain 定义 FE 自己的塔生态。

它回答的问题是：

- 分馏塔从哪里来。
- 分馏塔为什么可以越跑越强。
- 多余分馏塔为什么仍然有长期价值。

核心对象：

- 分馏塔原胚。
- 定向原胚。
- 四类实体分馏塔。
- 数据中心中的分馏塔当前库存。
- 献祭特质和塔种加成。

设计循环：

1. 原胚通过交互塔培养成实体分馏塔。
2. 实体分馏塔可以进入产线使用，也可以进入数据中心库存。
3. 分馏塔也可以回到原胚或定向原胚循环，形成塔生态内部流动。
4. 某类分馏塔在数据中心达到阈值后，献祭特质按运行节奏消耗当前库存的一部分。
5. 被消耗的实体塔转成对应塔种的当期运行加成。
6. 玩家后期通过原胚、返胚、定向原胚、塔库存和献祭加成形成自循环增殖。

关键设计思路：

- 分馏塔是实体资源，不是纯 UI 数值。
- 数据中心记录的是当前可提取库存，不是历史累计成就。
- 献祭消耗的是当前库存的一部分，因此玩家需要持续补充塔库存，而不是一次性达标后永久吃满。
- 献祭应按运行节奏自动发生，不能要求玩家逐个塔手动点击。
- 交互塔负责把塔生态跑起来，数据中心负责保存真实库存，献祭特质负责把库存消耗转换为塔种加成。
- 后期允许通过链条达到无限分馏塔；这条线的目标就是让工具生态自我增殖。

BuildingTrain 的配方和成长应围绕这些大类：

- 原胚培养：原胚到对应分馏塔。
- 返胚循环：分馏塔到对应原胚或相关原胚。
- 定向原胚：让玩家更稳定地补齐目标塔种。
- 塔种强化：让交互塔、矿物复制塔、转化塔、精馏塔分别获得长期加成。
- 数据中心消耗效率：让同样的实体塔库存消耗产生更稳定或更高价值的塔种收益。

边界：

- 不把每个培养方向拆成大量必须抽取的独立配方。
- 不把塔成长变成纯 UI 扣资源。
- 不让高回响卡住基础塔循环。
- 不保留点数聚集塔或点数聚集配方作为历史兼容玩法。

## MineralCopy：矿物复制与资源扩展

MineralCopy 定义资源复制线。

它回答的问题是：

- 玩家能怎样把资源本身扩展为更多同类资源。
- 复制线怎样从前期补资源，成长到后期自循环。
- 黑雾材料和外部 MOD 资源怎样接入复制体系。

核心对象：

- 基础矿物。
- 稀有矿物。
- 常规流体。
- 黑雾材料。
- 兼容 MOD 资源。
- 伴生副产物。

设计循环：

1. 输入资源本身。
2. 成功时以同资源增殖为主输出。
3. 失败时损耗或直通。
4. 伴生副产物体现资源关系，但不能压过同资源复制主线。
5. 随塔等级、配方等级、喷涂、回响和阶段成长，逐步从有损复制走向守恒和轻微净正收益。
6. 后期通过输入优先的自循环和富余输出形成稳定自动化资源扩展。

零压循环规则：

- 复制出来的同类主产物先补足塔内自循环输入。
- 塔内输入满足后，再补流动输出缓冲。
- 仍有富余时，才作为外部产物输出。

这个规则的设计目的：

- 让复制塔在自循环状态下优先维持自己运行。
- 避免塔把所有新产物立刻吐出，导致输入断流。
- 让“零压循环”成为后期资源自动化能力，而不是一次性爆产按钮。

MineralCopy 的配方和成长应围绕这些大类：

- 基础矿物复制。
- 稀有矿物复制。
- 流体资源复制。
- 黑雾材料复制。
- 兼容 MOD 资源复制。
- 伴生副产物强化。

基础展开：

- 基础矿物和常规流体应随阶段自然展开。
- 稀有矿物、黑雾材料、兼容 MOD 资源可以作为抽取单位、路线节点或阶段节点。
- 伴生副产物可以随主资源配方展开，也可以由回响增强。

边界：

- MineralCopy 不做普通材料转化。
- 普通材料转化不是资源复制线的职责。
- 不能让基础资源复制全部依赖抽取。
- 不能要求玩家逐个矿物手动点升级。

## Conversion：相关物品链转化

Conversion 定义相关物品链转化。

它回答的问题是：

- 某些同类或相关物品怎样在受限边界内互相转化。
- 随机转化怎样变成可规划产线。
- 低存在感消耗品、建筑层级和特殊链条怎样获得长期价值。

核心对象：

- 建筑升级链。
- 物流和运输链。
- 防御和弹药链。
- 燃料链。
- 消耗品链。
- 黑雾材料链。
- 兼容建筑或兼容消耗品链。

设计循环：

1. 输入某条相关链上的物品。
2. 按链条规则输出相邻层级、同层级、向上层级、向下层级或锁定目标。
3. 前中期以价值守恒或有损转化约束玩家进度。
4. 后期在成长投入后允许轻微净正收益。
5. 单路锁定把随机输出改造成可规划产线。

单路锁定设计思路：

- 玩家先接受链条的随机性，获得广义转化能力。
- 随成长推进，玩家可以把目标收束到某个方向。
- 锁定应消耗成长、效率、稳定性或资源投入，换取产线规划性。
- 锁定只在相关链条内部工作，不能把任意物品变成任意物品。

Conversion 的配方和成长应围绕这些大类：

- 建筑升级链：同类建筑低阶、中阶、高阶互转。
- 物流和运输链：配送运输机、物流运输机、星际物流运输船等。
- 防御和弹药链：炮塔、无人机、弹药、胶囊等军工物品。
- 燃料链：不同阶段燃料棒或同类燃料物品。
- 消耗品链：增产剂、爆破单元等有同类层级的消耗品。
- 黑雾材料链：黑雾材料之间的受限转化。
- 兼容建筑和兼容消耗品链：外部 MOD 中具有明确同类层级的物品。

边界：

- 禁止任意普通材料等价交换。这里的“普通材料”指铁块、铜块、电路板、处理器这类原版中间件和制造材料不能被做成任意互换池。
- 允许同类层级链或明确相关链转化，例如建筑升级链、物流运输链、防御弹药链、燃料链、消耗品链、黑雾材料链和兼容 MOD 中具有清晰层级关系的物品链。
- 禁止把 Conversion 做成万能等价交换。
- 禁止用转化绕过原版科技主链。
- 禁止把同一链条拆得过细，导致玩家必须抽大量方向配方。

## Rectification：精馏塔与矩阵精华

Rectification 定义矩阵精华线。

它回答的问题是：

- 矩阵除了原版科研之外，怎样成为 FE 内部实体资源。
- 精馏塔为什么不是“矩阵换残片”的薄包装。
- 高阶矩阵资源怎样通过压缩、回流、拆票和催化参与长期成长。

核心对象：

- 原版六色矩阵。
- 黑雾矩阵。
- 六种矩阵精华。
- 残片。
- 精华压缩、精华回流、精华拆票和精华催化。

矩阵精华的定位：

- 矩阵精华是实体资源。
- 它是阶段绑定票据，也是成长催化材料。
- 它可以拆成残片，但这只是用途之一。
- 它可以在精馏塔中压缩和回流，形成自动化调相链条。
- 它不能退化成“面板直接扣矩阵”的包装层。

六种矩阵精华使用 2 倍面值阶梯：

| 精华 | 残片面值 |
|---|---:|
| 电磁精华 | 2 |
| 能量精华 | 4 |
| 结构精华 | 8 |
| 信息精华 | 16 |
| 引力精华 | 32 |
| 宇宙精华 | 64 |

采用 2 倍阶梯的设计原因：

- 玩家可以直观看懂高低阶精华的价值关系。
- 压缩和回流可以围绕 2 倍关系表达守恒、损耗和轻微净正收益。
- UI 展示、配方说明和玩家心算成本更低。
- 黑雾矩阵不需要新增第七种精华，避免黑雾线和精馏经济过度绑定。

### 矩阵萃取

矩阵萃取把原版矩阵转成对应矩阵精华。

| 输入 | 输出 | 基础损耗 | 说明 |
|---|---:|---:|---|
| 电磁矩阵 | 电磁精华 x1 | 4% | 面值 2 残片 |
| 能量矩阵 | 能量精华 x1 | 4% | 面值 4 残片 |
| 结构矩阵 | 结构精华 x1 | 4% | 面值 8 残片 |
| 信息矩阵 | 信息精华 x1 | 4% | 面值 16 残片 |
| 引力矩阵 | 引力精华 x1 | 4% | 面值 32 残片 |
| 宇宙矩阵 | 宇宙精华 x1 | 4% | 面值 64 残片 |
| 黑雾矩阵 | 信息精华或引力精华 | 4% | 期望面值约 20 残片 |

黑雾矩阵设计：

- 不新增黑雾精华。
- 折算到信息和引力阶段。
- 让黑雾材料可以进入精馏经济，但不让黑雾成为独立货币层。

矩阵萃取成长路线：

| 等级 | 损耗 |
|---:|---:|
| Lv0 | 4% |
| Lv1 | 3% |
| Lv2 | 2% |
| Lv3 | 1% |
| Lv4 | 0.5% |
| Lv5 | 0% |

### 精华压缩

精华压缩把低阶精华向相邻高阶精华转换。

| 输入 | 输出 |
|---|---:|
| 电磁精华 | 能量精华 x 压缩倍率 |
| 能量精华 | 结构精华 x 压缩倍率 |
| 结构精华 | 信息精华 x 压缩倍率 |
| 信息精华 | 引力精华 x 压缩倍率 |
| 引力精华 | 宇宙精华 x 压缩倍率 |

压缩倍率成长路线：

| 等级 | 倍率 | 面值折算 |
|---:|---:|---:|
| Lv0 | 0.45 | 90% |
| Lv1 | 0.46 | 92% |
| Lv2 | 0.48 | 96% |
| Lv3 | 0.50 | 100% |
| Lv4 | 0.51 | 102% |
| Lv5 | 0.52 | 104% |

### 精华回流

精华回流把高阶精华向相邻低阶精华调整。

| 输入 | 输出 |
|---|---:|
| 能量精华 | 电磁精华 x 回流倍率 |
| 结构精华 | 能量精华 x 回流倍率 |
| 信息精华 | 结构精华 x 回流倍率 |
| 引力精华 | 信息精华 x 回流倍率 |
| 宇宙精华 | 引力精华 x 回流倍率 |

回流倍率成长路线：

| 等级 | 倍率 | 面值折算 |
|---:|---:|---:|
| Lv0 | 1.80 | 90% |
| Lv1 | 1.88 | 94% |
| Lv2 | 1.96 | 98% |
| Lv3 | 2.00 | 100% |
| Lv4 | 2.06 | 103% |
| Lv5 | 2.12 | 106% |

### 精华拆票

精华拆票把矩阵精华确定性拆成残片。

| 输入 | 输出 |
|---|---:|
| 电磁精华 | 残片 x2 |
| 能量精华 | 残片 x4 |
| 结构精华 | 残片 x8 |
| 信息精华 | 残片 x16 |
| 引力精华 | 残片 x32 |
| 宇宙精华 | 残片 x64 |

拆票规则：

- 拆票不吃成长倍率。
- 拆票不产源点。
- 拆票是矩阵精华的底层流动出口，不是精馏玩法深度来源。

### 精华催化

精华催化让矩阵精华参与 FE 其他成长。

设计思路：

- 精华可以为同阶段或低阶段的配方家族、路线节点、建筑成长或全局成长提供加速。
- 精华催化是资源消费，不是直接把矩阵当成长货币扣掉。
- 精华催化应保留阶段感：高阶精华可以支撑高阶目标，低阶精华不应无限替代高阶目标。
- 残片可以做底层补差，但不应替代精华链条。

边界：

- 源点不进入精馏配方。
- UI 面板不直接消耗矩阵作为 FE 成长货币。
- 精华拆票不能成为精馏唯一价值。
- 每种矩阵萃取不应都变成必须抽取的单项门票；矩阵阶段自然展开应承担基础入口。

## 配方成长与路线系统

分馏配方的成长不以“奖池”为内部核心，而以“成长入口”定义。

统一成长入口：

- 产线运行经验：自动化主来源，负责配方等级。
- 抽取重复命中：手动或半手动补差来源，负责回响或定向加速。
- 阶段自然展开：随原版科技、矩阵阶段、塔种阶段或资源可见性展开基础配方。
- 数据中心消耗：消耗实体塔、资源或精华，转成对应路线加成。
- 任务、成就和里程碑：一次性奖励或阶段性补差，不作为长期重复操作。

入口优先级：

- 产线运行事实是配方等级和路线成长的主来源。
- 阶段自然展开负责基础入口，不能被高回响、稀有抽取或高阶资源卡死。
- 抽取重复命中、残片、矩阵精华、数据中心消耗、任务奖励和里程碑只做补差、定向加速、阶段奖励或上限突破。
- 后期可以批量或策略化分配补差资源，但不能替代产线运行事实成为无限成长主来源。
- 手动入口必须有保底；自动化入口不需要保底，但必须能通过规模、时间和成长投入稳定收敛。

状态归属：

- RecipeKey 是底层分馏配方运行键，用于登记运行事实、产物事实和消耗事实。
- RouteState 是路线状态，存储路线进度、里程碑和已生效的一次性效果身份。
- 抽取单位、配方家族和路线可以一对多或多对一映射，但不能让同一成长状态同时由多个系统写入。
- UI 只能展示状态、发起请求和确认消费；具体成长、补差和效果应用由目标系统执行。

配方等级：

- 建议统一为 Lv0-Lv5。
- Lv3 是守恒或核心机制成型点。
- Lv4/Lv5 可以进入轻微净正收益，但需要玩家先投入矩阵、塔等级、配方成长和产线时间。
- 配方升级主来源是分馏塔产线运行事实，不能要求玩家逐条手动点击。

抽取单位：

- 抽取单位可以是一条具体配方、一组同类配方、一条转化链、一个塔种或一个精馏家族。
- 抽取单位不等于底层配方。
- 一个抽取单位可以映射到多个底层配方。
- 基础自动化路径不能被高回响卡住。

配方回响：

- 回响属于抽取单位，建议 0-3 档。
- 回响用于重复命中的长期价值。
- 回响提供附加效果、稳定性、补差能力或轻微效率提升。
- 没有回响也必须能完整运行基础自动化。

路线系统设计：

- RouteId 是稳定主键，但对代码语义是不透明键；不能依赖字符串拆分表达系统规则。
- RouteDefinition 定义路线目标、阶段、里程碑、效果和展示信息。
- RouteState 存储玩家在该路线上的进度、已达成里程碑和一次性效果身份集合。
- RecipeKey 是底层分馏配方运行键，用于把运行事实路由到对应路线，不作为路线状态的唯一抽象。
- 单配方成长也是 size-1 路线，不能留下孤儿成长状态。

里程碑效果：

- 里程碑效果是一次性或阶段性效果。
- 已生效的里程碑身份必须进入 sticky 集合。
- 不通过读回状态自动重发旧效果。
- 效果应用和里程碑身份写入必须是同一逻辑事务，避免重复发放。
- MilestoneEffect 应由目标系统本地解释，路线系统只负责派发和记录。

# 非分馏塔建筑

非分馏塔建筑是 FE 中不承担分馏热路径、但承担实体建筑能力和跨系统支撑能力的部分。

最终设计的核心非分馏塔建筑是物流交互站：

- 行星内物流交互站。
- 星际物流交互站。

它们不运行分馏配方，不承担抽取结果，也不决定路线成长公式。

它们负责把玩家的物流网络、数据中心和 FE 全局库存连接起来。

## 物流交互站

物流交互站回答的问题是：

- 物品怎样在物流站、数据中心和玩家产线之间流动。
- 数据中心库存怎样被自动上传和下载。
- 物流站怎样用建筑等级和点数池能力支持后期自动化。

核心能力：

- 上传：把交互站槽位中的物品传入数据中心。
- 下载：从数据中心把物品取回交互站槽位。
- 双向同步：按阈值同时处理上传和下载。
- 有限上传：遵守数据中心目标库存。
- 无限上传：把超出站内保留需求的物品持续上传。
- 槽位模式：每个槽位可以独立设置传输模式和容量模式。
- 能耗约束：上传下载应受建筑能力和电力预算影响。

设计原则：

- 物流交互站是建筑，不是 UI 页面。
- 它不生产资源，只负责搬运、同步和建筑能力转换。
- 它可以连接数据中心和物流网络，但不替代分馏塔自动化。
- 上传和下载必须保留物品数量和增产点数的真实流动关系。

## 数据中心

数据中心是 FE 的全局物品存储边界。

它回答的问题是：

- FE 的实体资源如何跨页面、跨建筑、跨产线使用。
- 奖励、上传、下载、抽取补差和成长消费怎样共享库存。
- 分馏塔实体库存、矩阵精华、残片、原胚和普通物品怎样统一存放。

数据中心负责：

- 全局物品库存。
- 上传和下载。
- 玩家背包访问重定向。
- 奖励入库。
- 分馏塔实体库存。
- 物品数量与增产点数的存储边界。

数据中心不负责：

- 决定物品价值。
- 决定路线成长公式。
- 决定抽取概率。
- 生产资源。
- 发放源点。

设计原则：

- 数据中心保存当前库存，不保存“历史上曾经拥有过多少”的成长幻觉。
- 可提取库存就是玩家能重新取出的实体库存。
- 某些成长或献祭可以读取并消耗当前库存，但这必须表现为实体资源减少。
- 数据中心可以为其他系统提供库存事实，但不能替其他系统解释玩法意义。

## 物流交互站增产点数池

增产点数池是物流交互站的支撑系统。

它回答的问题是：

- 数据中心里存放的增产剂怎样转化为自动补点能力。
- 物流交互站下载出来的物品怎样获得稳定增产点数。
- 为什么是“一次大量补充，多次少量消耗”。

核心设计：

1. 点数池从数据中心中的增产剂获得点数。
2. 当点数池不足时，系统一次性从数据中心取出一批增产剂，把它们折算成可用点数。
3. 后续每次下载物品时，不再逐个消耗增产剂，而是从点数池里扣除少量点数。
4. 这种设计把“增产剂实体消耗”和“每批下载补点”解耦，避免频繁读取数据中心，也让下载补点更平滑。

点数来源设计：

- 增产剂 MkI、MkII、MkIII 都可以转换为点数。
- 增产剂自身携带的增产点数也应计入可转换价值。
- 高级增产剂提供更多基础点数。
- 点数池不足时优先消耗高价值增产剂，以减少取物次数和库存碎片。

下载补点设计：

- 只对“本次从数据中心下载出来的批次”补点。
- 补点完成后，这批物品再合入物流交互站槽位。
- 不周期性扫描并改写槽内既有库存。
- 不因为槽内物品存在就凭空补点。

标准补点：

- 物流交互站达到自动补点门槛后，下载批次可以补到平均 4 点。
- 0 点到 4 点之间按 1:1 消耗点数池点数。
- 点数不足时，只补到点数池能支持的程度。

超载补点：

- 物流交互站达到更高等级后，下载批次可以从平均 4 点继续补到平均 10 点。
- 4 点到 10 点之间按 1:3 消耗点数池点数。
- 这段成本更高，表示 10 点是后期建筑能力，不是基础物流能力。

上传规则：

- 上传不额外补点。
- 上传时物品从交互站槽位拆出多少增产点，就带着多少增产点进入数据中心。
- 上传不是刷点入口，也不是把低点物品免费变高点物品的入口。

设计边界：

- 点数池只支撑物流交互站下载补点。
- 点数池不是分馏路线。
- 点数池不产出源点、残片或矩阵精华。
- 点数池不能替代增产剂生产链，玩家仍需要持续生产或储备增产剂。

## 堆叠扩展系统

堆叠扩展系统属于影响原版行为的底层系统。

它回答的问题是：

- FE 怎样提高产线吞吐和建筑容量。
- 哪些建筑或物流路径可以获得更高堆叠能力。
- 堆叠提升如何与塔等级、全局成长和原版限制共存。

它负责：

- 定义 FE 允许的堆叠上限。
- 为分馏塔、物流交互站、研究站、分拣器或其他相关路径提供堆叠边界。
- 让后期产线吞吐跟得上资源复制、精馏和转化能力。

它不负责：

- 决定分馏配方内容。
- 发放抽取结果。
- 解释路线成长。

设计边界：

- 因为它介入原版行为，所以必须和普通玩法系统分开看。
- 堆叠扩展是能力边界，不是独立主线。
- 堆叠扩展不能单独破坏原版科技阶段。
- 堆叠提升应绑定明确目标路径，例如分馏塔内部容量、物流交互站上传下载批次、研究站或分拣器等吞吐边界，不能全局无差别改大所有物品堆叠。
- 堆叠上限可以由原版科技、FE 全局成长、塔等级、路线里程碑或建筑特质共同决定，但每个来源必须能解释给玩家。
- 堆叠扩展不直接生产物品，只提高吞吐、缓冲和运行稳定性。

## 原版配方强化系统

原版配方强化系统属于影响原版行为的底层系统。

它回答的问题是：

- FE 怎样让原版制造链获得长期成长。
- 原版配方怎样与 FE 的矩阵精华、残片、源点或全局成长形成关系。
- 玩家为什么在后期仍然关心原版生产线效率。

它负责：

- 管理原版配方强化状态。
- 控制原版配方时间、上限、倍率或强化等级。
- 与矩阵阶段、堆叠扩展和全局成长形成约束关系。

它不负责：

- 定义 FE 分馏配方。
- 替代路线成长系统。
- 承担抽取或市场补给。

设计边界：

- 原版配方强化是对原版行为的增强，不是 FE 分馏主线本身。
- 强化应服务长期成长和生产节奏，而不是让玩家跳过原版科技链。
- 强化消费应遵守三层货币和矩阵精华边界。
- 原版配方强化只能作用于玩家已经能正常使用的原版配方或明确解锁阶段内的配方。
- 强化入口应由全局成长、矩阵精华催化、任务里程碑或明确的 FE 成长节点承接，不能由市场或抽取直接改写原版配方倍率。
- 强化可以影响时间、产量、能耗、上限或稳定性，但每个强化项都必须说明它改变的是哪一类原版行为。

## 黑雾战斗信息源

黑雾战斗信息源不是市场系统，也不是货币系统。

它回答的问题是：

- 其他系统怎样知道黑雾阶段、击杀、掉落、威胁和材料可见性。
- 黑雾扩展 MOD 的事实怎样被 FE 读取。

它负责：

- 提供黑雾阶段事实。
- 提供黑雾材料可见性。
- 提供战斗、掉落、威胁或隐藏科技相关事实。

事实粒度：

- 阶段事实：当前黑雾阶段、可见等级、隐藏科技或相关进度是否达到某个门槛。
- 材料事实：某种黑雾材料是否已经可见、可掉落、可复制或可进入兼容链。
- 战斗事实：击杀、威胁、掉落、遭遇或战斗进度等可被任务或路线读取的计数与状态。
- 兼容事实：外部黑雾扩展 MOD 提供的材料、科技、敌人或掉落是否存在。

它不负责：

- 市场补给。
- 路线成长写入。
- 抽取结果。
- 经济价格。
- 源点、残片或矩阵精华发放。

设计原则：

- 黑雾系统只输出事实。
- 任务、路线、抽取、解锁、市场等目标系统如果需要黑雾事实，由目标系统定义用途。
- 读取方只能读取黑雾事实并在自己的系统内解释用途；黑雾事实源不直接写路线状态、货币状态、抽取状态或市场状态。
- 黑雾不因为被其他系统读取，就变成原版影响底层系统。
- 第一版不新增黑雾精华，避免把黑雾强绑到精馏货币层。

# UI 面板

UI 面板负责查看、规划、手动确认、偏好设置和解释。

它不承担自动化生产。

UI 面板回答的问题是：

- 玩家从哪里理解系统。
- 玩家怎样设置方向。
- 玩家怎样确认一次性消费。
- 玩家怎样查看路线、成长、库存、任务、统计和教程。

## UI 面板的职责边界

UI 负责：

- 主面板入口。
- 抽取和偏好设置。
- 成长规划。
- 路线详情。
- 配方、塔种、建筑和精华状态展示。
- 数据中心上传下载和资源查看。
- 市场、兑换和有限救急补给。
- 任务、成就、图鉴、统计、教程和开发日记。
- 消费预览、确认和结果解释。

UI 不负责：

- 分馏热路径。
- 自动化生产。
- 物流站运行。
- 直接修改其他系统内部状态。
- 直接消耗矩阵作为 FE 成长货币。
- 凭空发放产线资源。

设计原则：

- UI 可以发起请求，不能绕过系统规则。
- UI 可以展示和确认消费，不能成为生产机器。
- 手动重复操作必须有保底。
- UI 外部入口应尽量简单，用少量选择承载更深内部策略。

## 主抽取与偏好

抽取系统回答的问题是：

- 玩家下一步往哪个方向发展。
- 随机性怎样提供方向，而不是制造无意义折磨。
- 重复抽取怎样转化为长期价值。

外部入口：

- 一个主抽取入口。
- 抽取前偏好设置。
- 成长规划和确定性补差。

外部不保留多个长期并列奖池。

设计思路：

- 玩家不需要频繁切换一堆池子。
- 玩家设置发展偏好，系统在内部按阶段、权重、路线、塔种、资源组和补差需求决定命中对象。
- 抽取命中的对象可以是配方、资源组、转化链、塔种、精馏家族、定向原胚或补差资源。
- 抽取重复命中后，优先补回响、补成长、补资源缺口或转成长期资源。
- 手动抽取必须有保底，避免无限重复无反馈。

偏好设计：

- 偏好是方向控制，不是生产按钮。
- 偏好可以控制路线优先、原胚优先、资源补差、精馏倾向或其他发展方向。
- 偏好应尽量少，让玩家能用少量操作表达目标。
- 内部权重可以复杂，但外部选择不能变成长期负担。

## 成长规划

成长规划回答的问题是：

- 玩家缺某条路线、某个塔种或某个配方家族时，怎样确定性补差。
- 自动化成长和手动补差怎样共存。
- 后期怎样批量、自动、按策略消费资源。

成长规划负责：

- 展示路线目标。
- 展示配方等级、回响和成长来源。
- 展示缺口和可用补差资源。
- 发起确定性补差请求。
- 按玩家偏好批量分配成长资源。

成长规划不负责：

- 替代产线运行经验。
- 把矩阵直接当 FE 成长货币扣除。
- 绕过路线解锁和阶段约束。

设计思路：

- 自动化产线运行是成长主来源。
- 抽取、残片、矩阵精华、任务奖励和里程碑用于补差或加速。
- 后期必须支持批量和策略化消费，不能让玩家逐条点配方。
- 成长规划要解释“为什么这个资源能补这个系统”，不能只显示一个扣款按钮。

## 三层货币系统

FE 货币分三层：

1. 残片。
2. 矩阵精华。
3. 源点。

### 残片

残片是底层成长货币。

负责：

- 常规补差。
- 低中层成长消费。
- 建筑突破和基础强化中的通用部分。
- 精华拆票后的底层流动出口。

边界：

- 残片不能稳定购买任意生产物资。
- 残片不能替代所有阶段资源。
- 残片不能承担源点职责。

### 矩阵精华

矩阵精华是阶段绑定票据和成长催化材料。

负责：

- 固定面值残片票据。
- 精华压缩和回流。
- 自动拆票。
- 同阶段或低阶段成长催化。
- 高阶成长消费中的阶段约束。

边界：

- 矩阵精华来自精馏链条，不是 UI 直接扣矩阵得到的虚拟货币。
- 矩阵精华可以支撑成长，但不能让精馏系统退化成残片提款机。

### 源点

源点是最高层点券式货币。

负责：

- 高价值抽取或定向选择。
- 关键补差、刷新、重置或跳过部分随机惩罚。
- 高阶全局成长或类似点券式入口。

来源白名单：

- 系统阶段奖励。
- 成就或任务的一次性奖励。
- 版本补偿、活动补给或调试/沙盒入口。
- 其他来源必须先写入本文档，再进入实现；不能用“类似入口”临时扩展。

红线：

- 源点不来自产线。
- 源点不来自市场买卖。
- 源点不由精馏塔产出。
- 源点不由稳定兑换产出。
- 源点不进入普通分馏配方。

## 市场、兑换和有限救急

市场系统回答的问题是：

- 玩家阶段性缺资源时，有没有有限救急机会。
- 市场怎样提供信息、缺口缓解和阶段补给。
- 为什么市场不能变成万能购买生产物资。

市场负责：

- 阶段性缺口补给。
- 有限订单。
- 市场指数、供需观察或资源趋势提示。
- 少量救急资源。

市场不负责：

- 稳定购买任意生产物资。
- 稳定卖物品换残片。
- 股票式生产物资买卖。
- 黑雾事实解释。
- 源点获取。

设计思路：

- 市场是缓冲器，不是核心产线。
- 市场可以帮玩家跨过短期卡点，不能替代资源复制、转化、精馏和原版生产。
- 市场补给应有限、阶段化、可解释。
- 市场救急必须有库存、订单、次数、冷却、阶段或价格约束中的至少一种硬限制。
- 市场不能提供稳定套利回路：不能稳定卖物品换残片，再用残片稳定买回更多生产物资。
- 市场补给的物品范围应以阶段缺口、引导和短期缓冲为准，不覆盖完整生产链。
- 黑雾追赶归路线、任务或成长规划解释，不归市场直接拥有。

## 任务、成就与全局成长

任务和成就回答的问题是：

- 玩家现在该做什么。
- 长期目标是什么。
- 跨系统行为怎样被汇总成奖励和成长。

它们负责：

- 主线目标呈现。
- 成就判定。
- 阶段奖励。
- 开发日记或图鉴解锁。
- 全局成长节点。
- 跨系统目标聚合。

它们不负责：

- 产线热路径。
- 抽取概率。
- 市场买卖。
- 黑雾事实采集。

设计思路：

- 主线不是顶层系统，而是多个系统共同呈现出来的玩家进度表达。
- 任务应引导玩家理解系统关系，而不是强迫重复操作。
- 成就可以提供一次性奖励、展示和长期目标，但不能成为稳定产线。
- 全局成长可以影响堆叠、效率、原版强化或阶段能力，但必须遵守原版进程和三层货币边界。

## 图鉴、统计和教程

图鉴、统计和教程回答的问题是：

- 玩家怎样理解系统。
- 玩家怎样复盘产线。
- 玩家怎样知道资源、配方、精华、路线和建筑之间的关系。

它们负责：

- 配方图鉴。
- 分馏统计。
- 资源流向解释。
- 路线和回响说明。
- 精华面值、压缩、回流、拆票说明。
- 教程和开发日记。

它们不负责：

- 改实际数值。
- 发核心奖励。
- 替代任务和成长系统。

设计思路：

- 复杂度可以存在于内部策略，但玩家必须能查到规则。
- 图鉴和统计应帮助玩家判断产线是否值得继续投入。
- 教程应解释承载面边界：分馏塔负责自动化，物流交互站负责流通和支撑，UI 负责规划和确认。

## UI 红线

UI 面板的红线：

- 不能承担自动化生产。
- 不能直接把矩阵当 FE 成长货币扣掉。
- 不能绕过分馏塔、物流交互站、数据中心或路线系统直接改状态。
- 不能把多个内部系统入口堆成长期操作负担。
- 不能让玩家为了基础自动化反复手动点击。

最终外部体验应是：

- 玩家看到的入口少。
- 玩家表达方向简单。
- 玩家能理解每项消费为什么发生。
- 产线、路线、精华、建筑和任务在内部形成深度联动。
- 前期手动选择有反馈，中后期重复行为被自动化替代。
